## 프로젝트 구조 정리

### 전체적인 Http11Processor의 요청 처리 흐름

```
(요점 : 일반 컨트롤러에서 처리 시도 -> 정정 컨트롤러에서 처리 시도 -> 그래도 처리 못하면 예외 응답)
```

- 일반 컨트롤러 리스트에서 요청 처리 시도
    - 일반 컨트롤러 중에서 요청을 처리할 수 있는 컨트롤러를 찾아 요청을 처리
    - 유의할점 : 일부 컨트롤러에서는 특정 분기일 때 일부로 요청을 처리하지 않고 무시하는 경우도 있다.
    - 일반 컨트롤러에서 처리하지 못한 요청은 단순 정적 파일 요청으로 간주

- 정정 파일 컨트롤러에서 요청 처리 시도
    - URI에 맞는 파일을 Resources/static에서 찾아 응답
    - 디폴트 확장자를 적용해 확장자가 없어도 일부 파일을 찾을 수 있도록 구현 (ex. "GET /login", login.html을 요청한 것으로 간주)

- 그래도 처리하지 못한 요청
    - 유효하지 않은 잘못된 요청으로 간주

### 일반 컨트롤러와 정적 파일 컨트롤러를 분리한 이유

- 우성 두 컨트롤러의 차이를 말씀드리겠습니다!
    - 일반 컨트롤러 : 요청에 대한 비즈니스 로직 처리후 리다이렉션 응답을 처리하는 컨트롤러
    - 정적 파일 컨트롤러 : 요청의 URI를 기반으로 resources에서 파일을 로딩하는 응답하는 컨트롤러

- 두 종류로 컨트롤러를 분리한 이유
    - 위에서 작성한 것처럼 두 종류의 컨트롤러가 서로 다른 책임과 역할을 수행한다고 판단했습니다!
    - 파일을 로딩해서 응답해야 하는 모든 요청을 하나의 정적 파일 컨트롤러에서 처리함으로써 요청 처리 흐름이 조금더 파악하기 쉽도록 하고 싶었습니다!
    - 파일을 로딩하는 복잡한 로직을 여러 컨트롤러에 중복으로 두고 싶지 않았습니다!
    - 또한 일반 컨트롤러에서 파일 로딩 관련 사항을 넣어 생각해야할 컨텍스트를 늘리고 싶지 않았습니다!

### 테스트가 통과하지 않는 이유

- 헤더의 대소문자
    - HTTP 명세에 따르면 헤더의 대소문자 구분이 없다고 합니다!
    - 하지만 테스트에서는 이를 허용하지 않기에 테스트가 실패합니다!
    - (실제 API 요청은 정상적으로 동작합니다!)

- 헤더 라인 끝의 공백
    - HTTP 명세에 따르면 헤더 라인마다의 끝에 공백을 붙이지 않는다고 합니다!
    - 하지만 테스트에서는 모두 공백을 추가하고 있어 테스트가 실패합니다!
    - (실제 API 요청은 정상적으로 동작합니다!)

- 위와 같은 이유로 현재 테스트가 통과하지 않아도 문제가 없다고 판단했습니다!

### 앞으로의 리펙토링 방향

- 프런트 컨트롤러 도입해 예외 응답 구성 (현재는 catch절에서 outputstream을 활용할 수 없어 예외 응답을 구성하지 못하는 문제 해결)
- 일반 컨트롤러에서 일부 분기에만 선택적으로 요청을 처리하는 경우 제거 (복잡도를 줄이기 위해)
