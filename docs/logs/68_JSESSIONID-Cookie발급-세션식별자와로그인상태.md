**프로젝트**: java-http

## 1. 출발점의 착각

처음에는 쿠키가 로그인 정보를 담고, 로그인 성공 때문에 `JSESSIONID`가 만들어진다고 생각했다.

실제 인과는 반대였다.

```text
세션 생성
→ 세션 식별자인 JSESSIONID 발급
→ 브라우저가 이후 요청마다 같은 ID 전달
→ 로그인 성공 시 서버가 그 세션에 사용자 정보를 저장
```

`JSESSIONID`의 존재는 로그인 성공을 증명하지 않는다. 같은 클라이언트가 같은 세션을 이어가려는 식별자일 뿐이다. 로그인 상태는 서버가 `JSESSIONID → Session`으로 조회한 뒤, 그 세션에 사용자 정보가 있는지 확인해야 알 수 있다.

## 2. 실제 Servlet과 이번 미션의 경계

실제 Servlet 컨테이너는 단순히 첫 요청이라는 이유로 무조건 ID를 발급하지 않는다. 애플리케이션이 `request.getSession()`처럼 세션 생성을 요청했을 때 세션과 식별자를 만든다. 로그인 전에도 세션은 만들어질 수 있다.

이번 미션은 세션 저장소를 만들기 전 단계라 다음 규칙만 먼저 구현했다.

```text
요청 Cookie에 JSESSIONID가 없음
→ UUID 발급
→ 응답 Set-Cookie에 JSESSIONID 추가
```

현재는 발급된 ID의 유효성 검증과 서버 세션 연결이 없다. 따라서 클라이언트가 임의의 `JSESSIONID=fake-id`를 보내도 존재 여부만 확인할 뿐, 실제 세션인지 판별하지 못한다.

## 3. 책임을 코드에 배치한 흐름

### Cookie

- 요청의 쿠키 문자열을 `;`로 분리한다.
- 각 조각은 첫 번째 `=`만 이름과 값의 경계로 사용한다.
- 잘못된 조각은 무시하고 정상 쿠키는 유지한다.
- 값이 없을 가능성은 `Optional<String>`으로 드러낸다.
- 헤더가 없을 때 `null` 대신 불변 빈 객체를 반환한다.

### HttpRequest

- Request Line과 헤더는 구조가 다르므로 구분한다.
- 이번 단계에서는 전체 `HttpHeaders` 리팩터링을 보류하고 `Cookie` 헤더만 추출한다.
- 헤더 이름의 대소문자는 구분하지 않는다.

### Http11Processor

- ID 생성은 쿠키의 책임이 아니라 서버 정책이므로 Processor가 맡는다.
- 모든 라우팅 응답이 만들어진 뒤 한 지점에서 `JSESSIONID` 존재 여부를 검사한다.
- 없을 때만 UUID를 만들고, 이미 있으면 재발급하지 않는다.
- 다음 단계에서는 이 책임이 `SessionManager`로 이동할 수 있다.

### HttpResponse

- 이번 미션 범위를 지키기 위해 전체 헤더 컬렉션 리팩터링 대신 쿠키 필드만 추가했다.
- `withCookie()`로 쿠키가 포함된 새 응답을 만들고 `Set-Cookie`로 직렬화한다.

## 4. 테스트

- `JSESSIONID`가 없는 요청 → UUID 형식의 `Set-Cookie` 응답
- 기존 `JSESSIONID`가 있는 요청 → 재발급하지 않음
- 여러 쿠키와 공백 파싱
- 값에 들어 있는 `=` 보존
- 잘못된 쿠키 조각 무시
- 요청 `Cookie` 추출과 응답 `Set-Cookie` 직렬화

`./gradlew :tomcat:test` 결과 21개 테스트가 모두 통과했다.

## 5. 이전 “바꿀 것” 적용

#19에서 남긴 “정리할 때 코드와 개념을 연결해서 설명하기”를 적용했다.

- 세션 식별자라는 개념 → `Cookie`
- 요청에서 식별자 수신 → `HttpRequest`
- 발급 정책 → `Http11Processor`
- 클라이언트로 전달 → `HttpResponse`
- 다음 요청에서 재사용 → 브라우저의 `Cookie` 헤더

개념 설명과 구현 책임이 시간 순서로 연결됐다. ✅

## 6. 학습 방식 회고

효과적이었던 점:

- “로그인해서 ID가 생긴다”는 착각을 “세션 ID는 있지만 서버 저장소가 없다면 무엇을 알 수 있나?”라는 반례로 교정했다.
- 새 개념과 책임을 먼저 합의한 뒤 테스트와 코드를 작성했다.
- 실제 Servlet 동작과 미션의 단순화된 규칙을 분리했다.

아쉬운 점:

- 초반에는 미션의 “없으면 발급” 규칙을 실제 Servlet의 일반 동작처럼 넓게 설명했다. 공식 명세를 확인한 뒤 세션 생성 시점의 차이를 교정했다.

다음에 바꿀 것:

- 교육용 미션 규칙과 실제 플랫폼 동작이 다를 수 있으면 처음부터 두 층을 나란히 표시한다.
